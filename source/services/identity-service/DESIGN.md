# Identity Service Design

## Scope

`identity-service` owns authentication, account lifecycle, branch-scoped RBAC, JWT issuance, refresh-token rotation, login audit, and identity domain events. Organization Service owns branch and employee business data; Identity stores only external `branchId` references required for authorization.

## Aggregates

### User

Owns credentials and account state.

Invariants:

- Username and email compare case-insensitively and must be unique.
- Only `ACTIVE` users without an effective lock may authenticate.
- Failed login attempts cannot be negative; reaching the configured threshold sets `lockedUntil`.
- Password change, administrative lock, and account disable increment `securityVersion` and revoke active refresh sessions.
- Password hashes use Argon2id or bcrypt. Plain credentials and tokens are never persisted or logged.

### Role

Owns a role and its permission set.

Invariants:

- Role code is stable and unique.
- A disabled role grants no effective permission.
- Permission codes use `resource:action`, for example `order:create`.

### RoleAssignment

Assigns one role to a user globally or for one external branch identifier.

Invariants:

- At most one active assignment exists for `(user, role, branch)`.
- `branchId = null` means global scope and must be restricted to authorized administrators.
- Effective time must be within `validFrom` and optional `validUntil`, and the assignment must not be revoked.

### RefreshSession

Represents one device session and token family.

Invariants:

- Only the current, unused token may rotate the session.
- Rotation marks the presented token used, inserts the new hashed token, and updates `currentTokenJti` in one PostgreSQL transaction.
- Presentation of an already-used token is reuse: revoke the entire family/session and emit an audit event.
- Redis key `lock:refresh:{sessionId}` may serialize instances, but the transaction must lock the session row and verify `version/currentTokenJti`.

## Application commands

| Command | Transaction and effect | Idempotency/concurrency |
|---|---|---|
| `Login` | Verify user, resolve permissions, create session/token, audit | Rate limited; uniform credential failure response |
| `RefreshToken` | Lock session row, consume old token, create new token, audit | Redis lock + row/version check; token JTI permits one rotation |
| `Logout` | Revoke one session and its remaining token | Repeated revoke succeeds safely |
| `ChangePassword` | Replace password hash, increment security version, revoke sessions, outbox | Idempotency key required |
| `CreateUser` | Create user and audit/outbox | Idempotency key + unique username/email |
| `AssignRole` | Create scoped assignment and audit/outbox | Idempotency key + partial unique index |

## Initial HTTP contract

All public routes are exposed through Kong under `/api/v1`.

| Method and path | Authentication | Result |
|---|---|---|
| `POST /auth/login` | Public, strict rate limit | Access JWT, opaque refresh token, effective permission/scope |
| `POST /auth/refresh` | Refresh token | Rotated access/refresh pair |
| `POST /auth/logout` | Access JWT or refresh token | Revoked device session |
| `GET /identity/me` | Access JWT | Profile and current effective authorization |
| `POST /identity/users` | `identity:create` + allowed branch scope | Created user |
| `PATCH /identity/users/{id}/status` | `identity:change_status` | Updated status and revoked sessions when required |
| `POST /identity/users/{id}/role-assignments` | `identity:assign_role` + branch scope | Created assignment |
| `DELETE /identity/users/{id}/role-assignments/{assignmentId}` | Same as assignment | Revoked assignment |

Return `401` for invalid authentication, `403` for insufficient role/branch scope, `409` for uniqueness/version/idempotency conflict, and `422` for domain validation.

## JWT and secrets

- Access JWT: 10–15 minute lifetime, asymmetric RS256/ES256 signature, `kid`, `iss`, `aud`, `sub`, `jti`, `iat`, `exp`, `securityVersion`, and compact authorization claims.
- Refresh token: opaque high-entropy value; persist only a slow hash or keyed digest suitable for lookup and compromise resistance.
- Signing keys come from a secret manager, not the image or migration. Local Docker stores a generated RSA pair in the private `coffee_identity_signing_keys` volume and reuses it across restarts; `GET /.well-known/jwks.json` publishes only the public JWK.
- Redis may cache effective permissions keyed by user/security version; invalidation follows role/assignment events.

## Migration V1

`V1__create_identity_schema.sql` creates users, RBAC, refresh-token family/history, identity audit, outbox, and idempotency tables. UUIDs are generated by the application so the migration does not require PostgreSQL extensions.

Deployment order:

1. Provision the dedicated `identity` database and least-privileged migration/application users.
2. Run Flyway V1 before starting application instances.
3. Deploy application code compatible with V1.
4. Seed permissions and the first administrator through a separate controlled bootstrap procedure; do not embed credentials in migration SQL.

V1 is forward-only after shared environments contain data. During local development only, rollback by dropping the dedicated identity database rather than maintaining a production down migration.

## Local Docker run

Create an uncommitted `.env` from `.env.example`, set a local database password, then run:

```powershell
docker compose -f compose.yml up --build -d
docker compose -f compose.yml ps
docker compose -f compose.yml logs identity-service
```

The default host ports are PostgreSQL `5433` and identity-service `8081`. Flyway runs automatically at application startup. Readiness is available at `http://localhost:8081/actuator/health/readiness`.

Stop containers without deleting database data:

```powershell
docker compose -f compose.yml down
```

Removing the named volume destroys the local identity database and must be an explicit decision.

## Implemented behavior

- Login uses a uniform `401` response for unknown users and wrong passwords; repeated failures apply a temporary lock.
- Access tokens are RS256 JWTs with `kid`, issuer, audience, expiry, security version, permissions and branch scopes.
- Refresh tokens are high-entropy opaque values; only SHA-256 hashes are stored. Rotation uses Redis owner-token lock plus a PostgreSQL row lock and detects reuse.
- Logout, status changes and role assignment revoke relevant refresh sessions.
- Account, role, permission and branch-scoped assignment writes store audit and outbox records in the same local transaction.
- Set `IDENTITY_BOOTSTRAP_ADMIN_USERNAME` and a bootstrap password of at least 12 characters for the first controlled local administrator. The bootstrap is skipped after that username exists.

Production must mount/provide an externally generated key from KMS/Vault and set `IDENTITY_JWT_GENERATE_IF_MISSING=false`. Local automatic generation is only a bootstrap convenience. Key rotation requires publishing old and new public keys during the access-token overlap window; the current local implementation exposes one active key.
